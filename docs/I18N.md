# Languages

Started 2026-08-02. Both shells speak English, German and Spanish — interface
and scripture.

## The rule

**User-visible text is core data, and a shell that spells a sentence is a bug.**

Half of this was already true before the project started: `panel.rs` generated
the guide, the about page and every study block. The other half was five hundred
string literals sitting in Svelte and Kotlin, and the reason they accumulated is
that nothing ever said no. `scripts/check-i18n.mjs` says no now, and it fails the
build.

## Where the words live

| | |
|---|---|
| `crates/core/src/i18n/en.json` | the source. Every string, keyed by a stable dotted id |
| `crates/core/src/i18n/de.json` | German. Overrides English key by key |
| `crates/core/src/i18n/es.json` | Spanish. Same |
| `crates/core/src/i18n.rs` | **the registry** (below), the catalogue, the fallback, `format`, `plural`, `resolve`, and the active language |
| `crates/core/src/canon.rs` | English book names. **Not** in en.json — see below |

`en` is the source, and a key another language lacks falls back to it. A reader
who meets one untranslated sentence is inconvenienced; a reader who meets
`hymnal.empty` is looking at a crash. `missing()` lists the gaps, and
`every_shipped_string_is_translated` fails the build over them, so the fallback
is a safety net rather than a hiding place.

**English book names stay in `canon.rs`.** That table is frozen and parsing reads
it too, so a second copy in en.json would be two sources for one fact and they
would drift. The catalogue OVERRIDES (`book.Gen` → `1. Mose`); the absence of an
override means English. `missing()` therefore cannot see an untranslated book —
`every_book_is_named_in_every_language` checks those directly.

## The registry

**A language is one row.** `SPECS` in `crates/core/src/i18n.rs` holds, per
language: its code, endonym and exonym; its catalogue; its corpus (file,
tokenization stamp, and the name a reader knows that Bible by); its Strong's
dictionary and whether that dictionary's definitions are machine-translated; a
modernization of its standard translation, if one exists; and a printed-numbering
table, if its tradition disagrees with the KJV's verse breaks.

Everything downstream reads the row:

| Reads it | Was |
|---|---|
| `corpus_for` (crates/ffi) | `match lang { De => "luther1912.jsonl", … }` |
| `strongs_for` | `active() == Lang::De && !cfg.strongs_de_off` |
| `canon::tokenization_is_ours` | a second hand-kept list of stamps |
| the modernization gate | a comparison against the KJV's tokenization |
| `versification::printed_as` | `if lang != Lang::De { return None }` |
| the renderings label on a study card | `if lexicon_de { "Luther" } else { "KJV" }` |
| `plumbline-hydrate`'s file list | a list that had never included `strongs-de.json` |
| `scripts/build-web-pack.mjs` | `GERMAN_TEXT`, `germanCorpus`, `germanLexicon` |
| the web loader's pack roles | `corpusRoleFor` returning a literal `"germanCorpus"` |
| the web home's install marker | `meta:germanInstalled` |
| the web's Settings | `if (code === "de")` |
| Android's bundled assets | a hand-written list in a test |

Two things carry it outward. **Over the ABI**, `WireLanguage` grew `bible`,
`corpusRole`, `lexiconRole` and `packFiles`, so a shell asks rather than knows —
`packFiles` being empty is the whole answer to "is there anything to download if
the reader picks this". **To the build scripts**, `plumbline-hydrate languages`
prints the registry as JSON; Node cannot read a Rust static, and the alternative
was a second copy of the table in `build-web-pack.mjs`.

`a_row_is_complete`, `each_variant_reaches_its_own_row` and
`no_two_languages_share_a_data_file` are what keep a new row from being
half-filled. The rows are indexed by the enum variant, so one inserted in the
wrong place would hand German the Spanish corpus with no other symptom — which
is why that anchor is asserted literally rather than derived.

**Adding a language** is a variant, a row, a JSON catalogue and the data files
the row names. `plumbline-hydrate languages`, the web pack, the Android asset
check, the eviction lists and the pin all follow.

## How a shell gets them

Two calls at startup, both engine-independent, both taking the reader's setting
AND the device's locale:

```
plumbline_i18n_set_language(chosen, device) -> resolved code
plumbline_i18n_catalog_json(chosen, device) -> { lang, strings, languages }
```

The catalogue covers what a **shell** spells. `set_language` covers what the
**core** spells — book names and references, in the TOC, search hits, weave
endpoints, note headers, thread entries, the reading map. Both, or a German
reader gets a German interface listing a book called Genesis, which reads as
broken rather than as a setting.

An empty setting means "follow the device", and `i18n::resolve` owns that rule so
the two shells cannot disagree about it. Writing `"en"` into the config the first
time a locale resolved would have frozen that reader into English permanently,
which is why absent is not the same as English here.

`i18n::active()` is a process global. Thirty places in the wire layer turn a
`VRef` into copy and every one of them would otherwise have needed a `lang`
parameter threaded from an engine handle several of them do not have. It is not
really global state: it is a property of the one reader the process serves.

## The web shell

- `apps/web/src/lib/i18n.svelte.ts` — one reactive table, `t()`, `plural()`.
  Filled from the boot reply, which carries the catalogue for the palettes'
  reason: the worker answers one thing at a time and no screen paints without it.
- `apps/web/src/lib/i18n.generated.ts` — the `boot.*` keys ONLY, generated into
  the JS bundle by `scripts/gen-i18n.mjs`. The splash paints in the first frame
  while the engine binary is still downloading, and a boot that FAILS never gets
  an engine at all, so those few strings cannot come from the engine.
- Changing the language reloads. The string table is reactive and would repaint
  on the spot, but book names come from the TOC, which is handed over once at
  boot and pinned because it cannot change while a session runs.

## The Android shell

- `apps/android/.../ui/Strings.kt` — the Kotlin twin: one table over a
  `mutableStateOf`, `t()`, `plural()`.
- Loaded in `onCreate` **before the engine opens**, because the table of contents
  is built at open and would otherwise be English for the life of the session.
- The picker recreates the activity, for the reload's reason above. The write is
  awaited first: `persistCfg` fires and forgets, which is right for a slider and
  wrong here.
- `Strings.seedForTest` + `CatalogForTest.kt` exist because a JVM unit test has
  no native library, so `t()` would answer with its own id and any test asserting
  on copy would fail for an unrelated reason. Those tests read `en.json`, so they
  check the sentence that ships.

Extracting Android found **eleven places where the two shells said the same thing
in different words** — written months apart and drifted. They are one wording
each now; the only survivor with its own key is `settings.bundledReloads`,
because the web reloads to apply the bundled study set and Android does not.

## The guard

`scripts/check-i18n.mjs`, run by `npm run check`, by the Android build, and by
its own CI job. In Svelte, three rules, and the third exists because the first
two missed something:

1. text nodes in markup
2. literals in speaking attributes (`aria-label`, `title`, `placeholder`, `alt`)
3. label-shaped properties in a script body (`label:`, `desc:`, `hint:`, …)

In Kotlin there is no markup/script split, so it checks the places a sentence can
legally sit in Compose: `Text(...)`, `contentDescription`, a `placeholder`/`label`
lambda, a `Toast`, and a copy-shaped parameter name or named argument. That last
rule exists because mutation-testing the checker caught it missing —
`backLabel: String = "Back to reading"` is copy on a screen and nothing else
looks at a signature. Matching on `: String = "…"` was the first draft and was
too broad (every wire default tripped it), so it goes by NAME, and `Wire.kt` is
skipped outright because every string in it is a protocol value.

It also checks the other direction: every id a shell asks for must exist. `t()`
answers an unknown id with the id itself, which is right at runtime and wrong at
build time — a typo would otherwise ship as a screen reading
`settings.cpoyFormat`.

Escape hatch: `i18n-ignore: why`, or `i18n-ignore-start` … `i18n-ignore-end` for
a run. The reason is required. There is one block exemption in the tree and it is
the honest kind — the boot-diagnostics tables render only under the PERF flag and
their contents are stage names out of the engine's own trace.

## What is deliberately still English

The welcome pages (`intro.welcome.*`, `intro.curious.*`). They are the
maintainer's own writing, in the first person, and a machine draft of that is not
a translation — it is words put in somebody's mouth in a language they cannot
check. They fall back to English until a person writes them.
`ENGLISH_ONLY` in `i18n.rs` is the list, and nothing else may join it.

The German and Spanish everywhere else are machine-drafted and say so in the
README.

One thing worth knowing about the German that is easy to miss: quotation marks
are language, not punctuation. German writes „low-high“ where English writes
“high-high”, which is why the marks around a quoted verse are `quote.wrap` in the
catalogue rather than typed into a component.

## The Spanish Bible

Reina-Valera 1909, public domain — the last Reina-Valera that is, since the 1960
most Spanish readers own belongs to the Bible societies. From the eBible.org USFX
edition via `seven1m/open-bibles`; built by `data-prep/rv1909/build-rv1909.py`
into `data/rv1909.jsonl` with its own stamp `rv1909-tok1`, and proved by
`check-rv1909.py`.

Three things came free with that source and are worth naming, because they are
why Spanish landed in one change:

- **It already sits at KJV addresses.** 66 books in canon order, 1,189 chapters,
  31,102 verses, every per-book chapter and verse count identical to
  `data/kjv.jsonl`. Reina-Valera follows the KJV's breaks throughout, so unlike
  German there is not even a printed-numbering difference to annotate — Spanish
  carries no `numbering` row, and `check-rv1909.py` proves it is entitled to
  none.
- **It is already Strong's-tagged**, inline, in the same file as the text. German
  needed a second edition and an alignment pass (`merge-strongs.py`) because its
  text and its tags came from different publishers; here they arrive together, so
  the tags are the source's own claim about its own words.
- **It marks translator-supplied words** with `<add>`, which is exactly what the
  KJV's italics are — so the reader's "italicize supplied words" setting means
  the same thing in both.

The one adjustment: the source tags PHRASES (`<w s="H8064">los cielos</w>`) where
`kjv.jsonl` tags only the head word. The build follows the KJV's convention, and
not for tidiness — the rendering lists are derived by counting the words standing
under each code, so phrase tagging put articles in the dictionary (H430 read
"Dios, de, tu"), and `occurrence_count` counts tagged tokens, so the same word
study would have reported three occurrences in Spanish where English reports one.

**The Spanish dictionary is whole, and the registry says so.**
`data/strongs-es.json` carries the Reina-Valera renderings — derived from the
tagged corpus, real data — under machine-translated definitions (a Claude
Sonnet subagent fleet, 2026-08-16; provenance and validation in
`data-prep/README.md`, with `translate.py` as the reproducible path).
`machine_translated: true` on that row is what shows the study card's AI
caveat, pointing readers at the repo's issues for corrections — the same
disclosure the German dictionary has carried since it shipped. The flag is the
honesty mechanism either way: while the definitions were still English it was
`false`, so the card could not claim a translation that had not happened.

## The German Bible

Luther 1912, public domain, from The Unbound Bible. Built by
`data-prep/luther/build-luther.py` into `data/luther1912.jsonl` with its own
stamp `luther1912-tok1`, and proved by `check-luther.py` — see
`data-prep/README.md`.

**Versification turned out to be a non-problem, and that was luck rather than
design.** That source has already been mapped to KJV numbering: all 66 books,
every chapter count, every last-verse number, 31,102 verses, identical to
`data/kjv.jsonl` in the same file order. German tradition numbers about 350
verses differently, and the Unbound editors moved the text to the KJV address
rather than renumbering, leaving the German number in the verse as a `3:19 `
prefix (stripped, and kept in `german-numbering.tsv`).

So **`refKey` means the same verse in both corpora.** No map, no migration, and
nothing a reader has written needs touching. The provenance stamp below shipped
anyway, because the next corpus may not be so accommodating.

### How the engine picks a text

`corpus_for(home, lang)` names the file **from the language's row**; `open_corpus`
opens it and **falls back to the KJV when it will not open**, which is the ordinary case rather than an
error — the German text is an optional download on the web. By trying rather than
testing for the file, because the web's home is a WASI shim where `Path::exists`
does not answer usefully; an existence check silently sent every German reader to
the English text.

The language must be set **before the engine opens**, since that is when the
corpus is chosen. On the web that is inside `boot()`; on Android it is in
`onCreate`. Setting it later — next to the table of contents, which is where the
web had it first — leaves a German reader on the English text with the download
sitting unused on their device.

**Morphology and the KJV's modernization are withheld from a text they were not
built against.** Both are keyed by (refKey, TOKEN INDEX) against
`kjv1769-tok2`, and another corpus tokenizes the same verse into different words
at different indices, so loading them would attach English grammar to whichever
Spanish or German word sat at that index.

The modernization is a COLUMN, not a special case. It used to be gated by
comparing the open corpus's tokenization against the KJV's, which reads as "this
feature is the norm and other languages are the exception"; it is one English
feature among the per-language columns now, exactly as Luther's verse numbering
is one German one, and `Lang::for_tokenization` picks it off the OPEN text
rather than off the reader's language — a German reader whose download has not
landed is on the KJV, and the AKJV is correct for them while they are.

Strong's is not withheld from anybody: the dictionary is keyed by code, and each
corpus now carries its own token tags.

### How it reaches a device

**Android bundles every language** in the APK (`syncData`, marker `.data-v6`) —
about 2 MB compressed each, and a reader in any shipped language has scripture
the moment the app opens. `bundled_data_marker_is_bumped_for_the_current_asset_set`
pins the gradle include list to the marker (two deliberate edits per data change,
because the marker is a device's only notice), and
`the_asset_list_carries_every_language_in_the_registry` fails until a new row's
files are on it.

**The web fetches them on demand**, `stage: "optional"`, when the reader picks
that language. Nothing on the web is ever bundled, so the only question was which
stage, and an English reader must not download a Spanish Bible to read Genesis
(`e2e/language.spec.ts` watches for exactly that request, for every language's
files rather than for German's by name). There is no separate Settings row:
picking the language IS the ask, so the picker downloads and then reloads.

`hasOptional` is asked **per file** rather than once per stage. It was a single
boolean while the suggested weaves were the only optional entry; a reader can
easily have one and not the other, and either answer would have made the pin lie
about half the set.

## The printed German numbering

`crates/core/src/versification.rs` — 357 verses out of 31,102 (about 1.1%) carry
a different verse number in a printed German Bible, because German tradition
breaks 26 books' chapters in slightly different places. The Unbound editors left
those numbers inline when they moved the text onto KJV addresses;
`build-luther.py` strips them and the table keeps them.

**It annotates, it does not renumber.** Where the two disagree, the study card
says "Maleachi 4,1  Luther 3,19", which is what lets a reader find a reference
somebody handed them. Chapter counts, navigation, search and the reading map all
stay on KJV numbering.

That was a deliberate choice over a full two-way versification layer, which would
touch every site that computes a chapter number and has 26 book boundaries to get
off-by-one wrong silently — to fix 1.1% of references. Explaining the difference
is more useful to somebody holding a printed Bible than quietly renumbering, and
**only Joel has a different chapter COUNT** (3 against 4); every other affected
book is a single verse on the far side of a break.

Because it comes from the core's block model, both shells show it with no shell
code.

## Loading: one corpus, not three

A corpus cache per language exists now and a reader may have several on the
device. Stage 1 must inflate only the one being read — `corpusRoleFor` in
`apps/web/src/engine/pack.ts`, which composes `corpus:<code>` by the same
convention the pack script files them under.
Until it did, a German boot gunzipped and copied ~63 MB into the home before any
text appeared, against ~35 MB for English, then evicted both. The boot trace's
`home evict after open (KB)` is the number that shows it: 64,739 with both,
28,371 with one.

Both stay in the pin and the depot — this decides what is INFLATED, never what is
kept, because switching back has to work offline and prune keeps what the pin
names.

The language for that decision is handed in by the main thread. `localStorage` is
main-thread only, and stage 1 runs in the engine worker; reading it there throws.

## Not done yet

**The Spanish Strong's definitions** — the renderings ship; the prose needs one
translation run. See the Spanish Bible above.

**Spanish hymn texts.** The hymnal keys texts by language code, so Spanish works
the moment texts exist, and there are none: the historic public-domain Spanish
translations of these hymns are real, but no source with verifiable attribution
and licensing was found, and a hymn stanza recalled from a model's memory and
published under a translator's name is a fabricated attribution, not a
translation. German stands at 31 of 90 for the same kind of reason.

**The Guide & About pages** — about forty paragraphs of instructional prose in
`panel.rs`, still English.

**A full versification layer**, if annotating ever proves insufficient. See above
for why it was not done.

## The provenance stamp

Every user-authored file carries `lang`: notes, threads, tags, weaves, memory
cards. It is written **at create, never on re-save**, and that asymmetry is the
whole design:

- A new file's refKeys are being written now, in the language being read, so the
  stamp is true.
- A file from an older build carries no stamp and must never gain one. If a
  German-reading owner edits a note written last year and the save wrote the
  current language, that note would claim German numbering it was never written
  in — a confident wrong answer where there was an honest absence, and the
  migration would act on it. **Absent means "unknown", not "English".**

It lives in each format's round-trip extra-keys map rather than as a modelled
field, because nothing in this build reads it. `i18n::stamped_extra` is the one
constructor; `crates/core/src/i18n.rs` carries the reasoning and the test that
the stamp follows the reader, and each format has a companion test that a
re-save invents nothing.

**Filtering on the stamp is a separate decision and is not made.** Hiding a
reader's own work in every list view because they switched language needs saying
on screen, and needs deciding once rather than per-screen. The stamp is what
makes it possible to decide later at all.
